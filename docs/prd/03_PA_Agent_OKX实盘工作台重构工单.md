# PA Agent OKX 实盘工作台重构工单

## 1. 文档状态

- 状态：执行中
- 范围：OKX Demo 首发；Longbridge 与 OKX Live 不在本阶段
- 目标版本：桌面快捷方式 `D:\Desktop\PA_Agent.lnk` 所加载的同一套代码
- 设计依据：用户提供的 3 张 PA Agent 截图、Longbridge 参考截图、当前代码、网页版 GPT 审核与 Stitch 视觉探索

## 2. 一句话目标

把现在拥挤的“实盘交易”弹窗改成主窗口一级工作区，让用户第一眼看清“系统是否在跑、账户现在怎样、本轮为何下单或不下单、订单走到哪一步、当前真正生效的风险配置是什么”，技术细节默认收起。

## 3. 不可破坏的事实

1. GUI 不是第二个交易执行器。所有券商写操作继续只经 `ExecutionController → ExecutionWorker → ExecutionService → OkxAdapter`。
2. GUI 只读取现有执行账本、Worker 控制库、Campaign 状态文件和账户快照，不增加第二套账本。
3. 自然 10 分钟 PA 判断继续运行；没有信号就明确显示不下单原因，不强行制造交易。
4. OKX Demo 与 OKX Live 必须持续可区分。本阶段界面只开放 Demo；Live 入口不伪装成可用。
5. `totalEq` 只用于资金流、高水位和 50% 回撤；USDT 权益只用于 OKX USDT 合约定仓。两个数字都可展示，但不能混算。
6. 已经发往券商但结果不明的命令才是 `UNCERTAIN`；写前被风险闸门拒绝是 `FAILED/BLOCKED`，禁止自动重发。

## 4. 现状问题

### P0：入口和信息层级错误

- “实盘交易”是一个 `780×680` 的模态弹窗，无法和行情、PA 判断、订单进度并行观察。
- 运行状态、配置、路由、账户、持仓、执行表和技术字段纵向堆叠，窗口高度不够时内容被压缩。
- `instId`、API 地址、Worker 状态码、路由映射等后端术语占据主视觉。
- “桌面手动会话”和“自动 Campaign”并列但没有清楚解释两者关系，用户难以判断哪个值正在控制交易。

### P0：配置语义不完整

- 当前只真正支持“固定资金上限 × 风险比例 → 动态张数”。
- “基础数量”对 Campaign 又会被风险引擎覆盖，字段名称会让用户误以为自己设置的张数正在生效。
- 运行中 Campaign 会冻结启动参数，但界面没有把“当前生效值”和“已保存、下次启动生效值”并排展示。

### P1：交易反馈不完整

- 最新 PA 决策、风险计算、监督结果、订单提交、成交、保护、离场没有形成一条人能快速扫读的时间线。
- `blocked:no_order`、风险拒绝、模型失败和券商失败混在一行文字里，无法区分“策略决定不下单”和“系统坏了”。
- 执行表字段过多，主表没有优先展示方向、张数、入场、止损、当前状态和结果。

## 5. 第一版信息架构

主窗口增加两个一级工作区：

1. **分析工作台**：保留现有 K 线、AI 分析和决策过程。
2. **实盘交易**：新的 OKX Demo 交易工作台，不再弹出旧配置大窗口。

实盘交易工作台采用四区布局：

- 顶部固定状态带：`OKX 模拟盘`、Campaign 状态、Worker/对账状态、最后更新时间、刷新按钮。
- 中央主区：最新 PA 决策与执行生命周期；这是最大区域。
- 右侧固定栏：账户资金、风险停止、当前生效配置、待生效配置。
- 底部时间线：最近若干轮 10 分钟判断，以及当前/最近一笔执行从计划到关闭的关键节点。

高级技术信息放入默认收起的“技术详情”：账户身份摘要、`instId`、命令 ID、execution ID、原始错误码、数据来源和采集时间。

## 6. 定仓模式

两种模式互斥，同一时间只能选一种。

### A. 按风险预算自动算张数（默认）

用户可改：

- 资金上限 `C_cap`
- 单笔最坏损失比例 `r`
- 最大允许杠杆 `L_max`

系统只读计算：

- 有效风险资本 `C_eff = min(最新 USDT 权益, C_cap)`
- 风险预算 `R = C_eff × r`
- 单张最坏损失 = 止损价差损失 + 往返手续费 + 保守滑点
- 合约张数 `Q = floor_to_lot(R / 单张最坏损失)`

随后再检查 OKX 最小张数、步长、最大可开张数和杠杆容量。容量不足时明确阻断或进入已有的确定性杠杆计划，禁止静默截断张数。

### B. 用户固定合约张数

用户可改：

- 固定合约张数 `Q_fixed`
- 最大允许杠杆 `L_max`
- 资金上限继续作为硬保护上限，不参与算张数

系统只读反算：

- 本笔最坏损失金额
- 本笔最坏损失占有效风险资本的比例
- 所需保证金与名义价值
- 当前杠杆容量是否足够

如果固定张数超过 OKX 容量、低于最小张数、不是合法步长，或反算风险超过 100%，明确阻断。系统不能偷偷改小张数。

### 三者关系

- 张数和止损距离共同决定“最坏损失”；杠杆主要改变保证金占用与券商最大可开张数，不直接改变止损价差造成的损失。
- 风险预算模式中，用户设置资金和风险，张数由系统算出，张数不可手改。
- 固定张数模式中，用户设置张数，风险金额和风险比例由系统反算，风险比例不可手改。
- 两种模式都保留最大杠杆上限；系统只允许使用不超过该上限且经过 OKX 回读验证的杠杆。

## 7. 前端状态语义

界面必须明确区分：

- **正在生效**：运行中 Campaign 状态文件冻结的值。
- **待下次启动生效**：已保存到 `settings.json`、但当前 Campaign 尚未加载的值。
- **已确认事实**：券商回读、Worker 心跳、执行账本终态。
- **计划/计算值**：PA 决策、风险计算和待执行计划。
- **未知**：数据过期、读取失败或结果尚未确定。

保存配置不会自动重启 Campaign，也不会在后台热切换交易参数。配置不同步时必须显示醒目的“待下次安全重启生效”。

## 8. 主要交互

1. “分析工作台 / 实盘交易”在主窗口一级页签切换。
2. 主页面默认只开放：
   - 保存配置
   - 只读刷新
   - 启用/停用桌面手动会话
   - 对已有执行撤销入场或主动离场
3. 不提供绕过 PA 的直接买入/卖出按钮。
4. 任何会新增风险的动作仍需现有确认文本和租约；撤单、保护与离场不受新增风险停止拦截。
5. 配置一旦编辑，旧手动会话立即失效；保存成功后仍需重新启用。
6. Campaign 的启动、恢复和风险停止恢复不伪装成普通配置按钮。若以后加入，必须通过现有唯一 Worker 和明确的安全检查。

## 9. 视觉规范

- 目标画布：`1920×1080`；`1440×900` 仍需完整可用。
- 正文字号不低于 14px；关键金额/状态 18–24px；页标题 24–28px。
- 8px 基础间距；区块内边距 16–20px；主要列间距 16px。
- 深色背景沿用现有令牌：主背景 `#0d1117`、表面 `#161b22`、边框 `#30363d`。
- 强调色：蓝 `#58a6ff`；正常绿 `#3fb950`；警告黄 `#d29922`；阻断红 `#f85149`。
- 圆角最多 4px，不做大量悬浮卡片；使用清晰分栏、分隔线和固定对齐。
- 状态不只靠颜色，必须同时有文字和图标/形状。

## 10. 后端改动

1. `OkxExecutionSettings` 增加明确的 `sizing_mode`，复用现有 `quantity` 作为固定张数输入。
2. 风险模块新增固定张数反算函数，输出与自动定仓相同结构的耐久审计快照。
3. Campaign 指纹和状态文件冻结定仓模式、固定张数、资金上限、风险比例和最大杠杆。
4. 风险预算模式继续执行现有公式；固定张数模式校验张数并反算风险，绝不静默改量。
5. Supervisor、计划和 Worker 提交前仍要求同一份冻结数量与风险快照；提交前账户或规格变化导致结果变化时旧计划作废。
6. 只读工作台快照补充机器可用的 Campaign 原始字段，GUI 不再解析拼接后的长句。

1. 主窗口存在“分析工作台”和“实盘交易”两个一级页签；点击菜单“实盘交易”直接切到工作区，不打开旧大弹窗。
2. `1440×900` 下无需把窗口拖到屏幕外即可看见运行状态、最新决策、账户、风险配置和执行时间线。
3. 普通用户视图不出现 API 地址、Worker ID、execution ID 和原始路由字段；这些只在收起的技术详情中出现。
4. Campaign 当前值与已保存待生效值分别显示；两者不一致时明确标红/标黄。
5. 风险预算模式下张数只读，资金上限、风险比例和最大杠杆可编辑。
6. 固定张数模式下张数可编辑，风险金额和风险比例只读反算。
7. 固定张数不合法、超过容量或风险超过 100% 时明确阻断，券商写请求为 0。
8. 两种模式的最终数量在 PA 记录、Supervisor 输入、ExecutionPlan 和 Worker 写前复算中完全一致。
9. `totalEq` 不参与定仓；USDT 权益不参与资金流高水位计算。
10. 配置编辑使旧手动会话失效；保存不会自动重启 Campaign。
11. 最新 10 分钟轮次能区分“策略不下单”“风险阻断”“模型失败”“券商/系统失败”。
12. 一笔执行能显示计划、监督、提交、成交、保护、撤单/离场和终态；未知写入禁止重复按钮。
13. GUI 不直接调用 OKX 下单接口；所有写操作仍只经过唯一 Worker。
14. OKX Demo 的自然交易和监测在开发期间继续；不因 GUI 开发强制制造订单。
