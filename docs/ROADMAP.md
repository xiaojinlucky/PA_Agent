# PA_Agent 统一路线图（本机适配版 v2）

> 本路线图吸收网页版 GPT / Biomni 的规划，但不是本机事实的替代品。当前能力以代码、当前测试和本机实时核验为准；目标行为以已确认 PRD 和用户决定为准。网页版 GPT 看不到本机 skills、memory、进程、未提交工作区、真实配置和券商私有状态，因此它只能发工单与硬验收，本机 Codex 必须在执行前按真实环境改写工单假设。
>
> 本版修订原则：阶段 0 压缩为一次文档冻结；先打通无界面自动分析主脊柱，再做完整界面；Longbridge 移出 OKX 首发主路线；K 线时间、多周期和成交量暂作研究假设；全程 Demo 验收，Live 只在最后作为单一开关。

## 本机执行适配

- 项目 checkout：`D:\Desktop\Quant\PA_Agent`；Windows；Python 使用项目 `.venv\Scripts\python.exe`，不能把全局 Python 的结果当成本项目结果。
- 每张工单开工前先读 `CONTEXT.md`、`lessons.md`、`docs/CODEX_PROJECT_RULES.md` 和 `docs/LOCAL_EXECUTION_CONTEXT.md`；再按工单需要读取本机实际源码、测试、运行态和 PA_Agent 相关 memory。memory 只提供历史决定和经验，不能代替本机实时证据。
- PA_Agent 不是 open-xquant；不能把 open-xquant 的 skills、规则或执行假设当成 PA_Agent 的现成实现。网页设计默认不以 Figma/Figma MCP 为前置条件，后台接口稳定前不改生产 PyQt 视觉。
- 任何交易功能都保持 `ExecutionWorker` 为唯一券商写入者；AI、监督智能体、GUI、自动协调器和 `ExecutionController` 只产生结构化意图、计划或持久命令。
- 研发、测试、审查和规划不发送真实订单。OKX 私有只读核验只有在具体工单需要且授权边界明确时才做；Live 开关或容量的历史描述不能替代现场核验。
- Git 发布必须按明确文件清单暂存，禁止 `git add .` / `git add -A`；只扫描 staged snapshot 的密钥、数据库、日志、运行态和大文件；不擅自开分支、worktree、改写历史或推送 `upstream`。

## 终态

PA_Agent 的终态是 Windows PyQt6 桌面上的 OKX 永续全自动交易控制台：首发单品种 `XAU-USDT-SWAP`、15 分钟、单策略、单 PA 专用账户、USDT 本位、全仓、净持仓、可多可空。AI 只产生结构化交易意图；确定性规则负责账户、品种、数量、杠杆、保证金、客户订单号、幂等、对账和恢复；`ExecutionWorker` 是唯一券商写入者。

**“全自动”= 日常运行不逐笔等待人工确认。** 它不代表绕过以下部署授权和执行完整性规则：

- 首次打开真实交易，用户手动开闸一次。
- 断网或账户身份不匹配时，停止新增风险。
- 订单结果未知时，先按客户订单号对账，绝不盲目重发。

## 三层状态模型（不改现有枚举）

1. `ExecutionState`：一笔执行记录的状态，现有 13 态，负责券商受理、成交、保护、退出和未知等逐笔事实。
2. `PositionLifecycle`：一笔父级仓位从首仓到最终退出的生命周期，属于阶段 3 目标态；它引用逐笔 `ExecutionState`，不覆盖逐笔事实。
3. `AutomationState`：整个自动交易系统的运行、暂停、停止和恢复状态，阶段 1 先形成雏形，阶段 4 完整；它不能代替环境硬门、Worker 心跳或执行状态。

映射原则：自动循环可以处于 `WAITING_BAR`、`ANALYZING`、`SUPERVISING` 等目标状态；父级仓位可以处于 `FLAT`、`ADDING`、`REVERSING_ENTRY` 等目标状态；这些状态必须独立建模，不能擅自塞进或改写现有 `ExecutionState`。

## 阶段路线（进攻式顺序：先让系统自己跑，再让界面看清它）

### 阶段 0：真值冻结（压缩版，当天完成）

- 目标：当前态文档与当前代码一致，冻结当前态/目标态真值优先级，落库正式 PRD 与本路线图。
- 只改文档，不改交易执行逻辑，不改状态枚举，不发订单。
- 一个 PR、最多两个 commit；完成后立即进入阶段 1，不继续经营文档会议。

### 阶段 1：无界面自动分析主脊柱（当前下一阶段）

- 目标：让第二个智能体（交易监督）进入现有无界面 Campaign，并把分析、监督结论和 K 线唯一处理键持久化。
- 核心链路：

  ```text
  OKX 15 分钟已收盘 K 线
      → PA 两阶段分析
      → 交易监督智能体
      → 保存监督结论
      → Demo 中拒绝阻断计划、放行沿用现有 Controller/Worker
      → 等待下一根 K 线
  ```

- 本阶段不触碰 Live，也不发送真实订单；“不改变真实下单行为”是指不改变 Live/真实交易边界，不是做无效影子分析。经授权的 Demo 和离线 Fake 运行必须真实证明拒绝不建 execution、放行最多一笔计划和一条 `SUBMIT` 命令。
- 必须做到：GUI 关闭后仍能运行；重启后同一根 K 线不重复处理；主模型失败切备用模型；两个模型都失败确定性拒绝；输入、输出摘要、模型版本和监督结论可追溯；监督智能体能读取脱敏账户与当前执行状态。
- 首张工单 `WO-S2A-01` 已完成本机适配实现和离线硬验收：监督结论严格建模、已配置备用时主备同快照、原子落盘、重启复用、拒绝不建计划、放行沿用现有 Controller/Worker；未修改 `pa_agent/execution/`，未触碰 Live。监督备用档案需要本机设置明确绑定，空绑定会确定性阻断；PA 备用档案已做配置级独立验证，完整 PA 分析备用切换留给后续专门工单。
- 下一张工单：`WO-RISK-02`，先替换当前 Demo 的 `equity_10pct_notional` 技术仓位算法。

### 阶段 2：单仓全自动闭环（Demo）

- 目标：打通一次完整交易闭环，先不做加仓和反手。
- 核心链路：

  ```text
  PA 信号 → 监督放行 → 10% 止损风险计算 → 动态杠杆
  → 自动入场 → 自动建立保护 → 自动退出
  ```

- 全程 OKX Demo；Demo 与 Live 共用同一套 Controller/Worker/执行链，只靠确定性配置切换环境。本阶段的 `equity_10pct_notional` 只能作为旧 Demo 技术算法，不能冒充正式 10% 止损风险算法。
- 下一张风险工单：`WO-RISK-02`，用入场价、止损价、`ctVal`、`ctMult`、`lotSz`、`minSz`、费用、滑点和最大可开张数计算正式数量。

### 阶段 3：进攻型仓位管理（Demo）

- 目标：加入同向加仓、加权平均成本、统一保护、TP1 后重新管理、减仓、平仓反手和父级交易生命周期。
- 主要改动：风险引擎扩展、`PositionLifecycle` 父级模型、逐笔执行腿、保护版本和生命周期锁；反手必须先确认旧仓归零。
- 进入条件：阶段 2 单仓闭环验收通过。

### 阶段 4：持续运行机制（Demo 验收，实盘开关就绪）

- 目标：持久自动运行状态、首次开闸一次、重启自动恢复、暂停新开仓、紧急清仓、连续三次完整止损暂停、50% 回撤停止和资金流水校正。
- 重启只在恢复门禁通过时恢复新增风险；未知写操作只对账，不自动重发。
- 阶段结束时才提供明确的“启用实盘”路径，且强制前置 OKX Live 最小权限整改和用户明确授权。

### 阶段 5：前端落地与复盘

- 目标：长桥风格工作台、两个智能体统一交易链视图、持仓与风险、自动运行状态、暂停与紧急清仓、完整复盘。
- 设计线可在阶段 0 后并行：事实校准 → Stitch 高保真 → GPT 按真实后端审图 → 接口稳定后落地 PyQt6。完整七页界面不阻塞阶段 1–4。
- 进入条件：阶段 4 停止与恢复机制验收通过。

## 移出 OKX 首发主路线的内容

- Longbridge 的限速、私有推送和三账户扩展：归入 OKX 首发闭环完成后的多券商路线，不参与阶段 0–4 验收。
- K 线时间、多周期和成交量：暂作研究假设。先做高周期背景标签实验（只作置信度背景，不硬性否决已成立的 15 分钟信号），再做 session 标签；全自动闭环完成前不因这三点改写 PA 决策树。
- 多品种、多策略、多账户、NautilusTrader 切换、完整回测和绩效统计：不阻塞首发主链。

## 每张工单共同硬验收

1. `ExecutionWorker` 仍是唯一券商写入者，不出现第二套订单账本或写入链。
2. 计划、命令入队、券商受理、部分成交、成交、保护和平仓分别建模。
3. 同一已收盘 K 线、分析记录或持久命令不能重复产生新增风险。
4. 模型不能修改账户、数量、杠杆、保证金、品种、客户订单号或券商路由。
5. 未知写结果先对账，禁止盲目重发。
6. 报告真实通过、失败、跳过和超时数量；全量测试的既有失败必须与本轮回归分开报告。
7. staged snapshot 无凭据、数据库、日志、运行记录和不明大文件。
8. 分别报告本地 HEAD、远程 HEAD、实际修改文件和未提交工作区。
9. 复杂工单完成后做独立审查，覆盖需求、逻辑、边界、代码质量、测试和实际运行；阻塞项不为 0 不得闭单。
